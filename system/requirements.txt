# PRAXIS dependencies, pinned exactly. §2 forbids adding to this list casually.
#
# Not present, and deliberately: cloud SDKs, telemetry, analytics, feature flags, a broker
# other than Redis, an ORM other than SQLAlchemy, or anything that phones home. R6 is tested
# against this file as well as against the source.
#
# requirements.lock carries the hashes and is what an install should use. See D15.
#
# Every pin below is the version the suite actually passed on, read back from the installed
# environment rather than chosen. See D41: a pin that nobody has run is a guess, and installing
# from a guess is how a reproducible run stops being reproducible.
#
# That rule applies to the lock's transitive pins too, and it had stopped being true of them. A
# plain `uv pip compile` resolves against whatever PyPI offers on the day, and the lock had
# drifted ahead of this machine in forty packages - starlette 1.7.0 against the 1.3.1 the media
# endpoint's range tests were written and measured on, among them. None of those forty was a
# direct dependency, so nothing here had moved and nothing looked wrong. Regenerate both locks
# together, and constrain the universal one to what is installed:
#
#   python scripts/freeze_constraints.py
#   python -m uv pip compile requirements.txt --universal --generate-hashes \
#       --constraint constraints.generated.txt -o requirements.lock
#   python -m uv pip compile requirements.txt --python-platform x86_64-unknown-linux-gnu \
#       --python-version 3.14 --generate-hashes \
#       --extra-index-url https://download.pytorch.org/whl/cpu \
#       --index-strategy unsafe-best-match -o requirements.linux-cpu.lock
#
# The second has no constraint and must not have one: it is the resolution a platform this suite
# has never run on will get, and pinning it to Windows-measured versions would be a claim about
# an environment nobody measured. Its header says so, and says why the container needs its own
# file at all. uv rewrites that header on every compile, so the prose above the generated line
# in that file has to be put back by hand.
#
# The consequence of leaving it unconstrained is that the container resolves starlette 1.7.0
# while this machine holds 1.3.1, and the media endpoint hands HTTP Range handling entirely to
# starlette's FileResponse. That was checked rather than assumed: the same 55 MB blurred file was
# served through both, and all nine cases the range tests assert came back identical - full body,
# an exact 100-byte window, open-ended, suffix, 416 carrying the true size, a clamped overrun,
# 400 on a malformed header, multipart/byteranges at full length, and HEAD with no body. No
# `content-disposition` from either, which is R1 and D76. So the versions are not forced to
# match, and the reason they need not be is written down here rather than rediscovered.

# Both were installed but undeclared, which is the drift this file exists to stop, and both earn
# the line they take up.
#
# pytest-randomly shuffles the order every run and prints the seed it used, so a failure stays
# reproducible with `-p randomly --randomly-seed=<n>`. It is here because six tests were found
# passing by file and failing by suite: each asserted a corpus-wide figure against a database
# that other tests had written to, and in a fixed alphabetical order that stays green until a
# new test file sorts earlier. A fixed order cannot find that class; this can.
#
# pytest-xdist gives each worker its own process, and so its own session scratch database. `-n
# auto` is a convenience on a six-minute suite rather than a guarantee of anything, and the
# ordering guard above is what the correctness argument rests on.
